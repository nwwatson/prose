# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Prose is a Ruby on Rails 8.1 application (Ruby 3.4.13) using the "Solid" stack — SQLite3 for all persistence with Solid Queue, Solid Cache, and Solid Cable for jobs, caching, and WebSockets respectively. No external services (Redis, etc.) are required.

Frontend uses Hotwire (Turbo + Stimulus), Tailwind CSS, Propshaft asset pipeline, and ImportMap for JavaScript modules.

## Common Commands

### Development
```bash
bin/setup              # Full dev environment setup (idempotent), starts server
bin/setup --skip-server # Setup without starting server
bin/setup --reset      # Reset database during setup
bin/dev                # Start dev server (Puma + Tailwind watcher on port 3000)
```

### Testing
```bash
bin/rails test                        # Run all unit tests
bin/rails test test/models/user_test.rb  # Run a single test file
bin/rails test test/models/user_test.rb:15  # Run a single test by line number
bin/rails test:system                 # Run system (browser) tests

```

### CI Pipeline
```bash

bin/rubocop            # Ruby linting (rubocop-rails-omakase style)
bin/brakeman --quiet --no-pager --exit-on-warn --exit-on-error  # Security scan
bin/bundler-audit      # Gem vulnerability audit

```

### Database
```bash
bin/rails db:prepare   # Create and migrate database
bin/rails db:migrate   # Run pending migrations
bin/rails db:seed      # Load seed data
bin/rails db:reset     # Drop and recreate from schema
```

The app uses `config.active_record.schema_format = :sql`, so **`db/structure.sql` is the
authoritative schema** — SQL format is required to preserve the FTS5 virtual tables and
triggers that Rails' Ruby schema dumper cannot express. There is no `db/schema.rb`; it is
gitignored, and `db/*_schema.rb` (the generated Solid Queue/Cache/Cable dumps) plus
`db/schema.rb` are excluded from RuboCop in `.rubocop.yml`.

## Architecture

Refer to `docs/design_guide.md` for comprehensive architectural patterns. Key principles:

### Model Organization
Models use **concerns for behavior composition**. Each concern lives in a directory matching the model name:

Keep model files under 200 lines — extract behavior into concerns when they grow.

`has_many` associations whose children have no callbacks, attachments or dependents of their own use `dependent: :delete_all` (`post_tags`, `post_views`, `post_versions`, `reading_list_items`, `fediverse_likes`, `newsletter_deliveries`, `subscriber_labelings`, `webhook_deliveries`), so destroying a parent issues one DELETE per table instead of one per row while holding SQLite's writer. Giving one of those child models a destroy callback, attachment or dependent means switching its parents back to `:destroy`. Don't add a single-column index that a composite index on the same table already starts with.

### Controller Pattern
Skinny controllers that delegate to models/services. Controllers handle only HTTP concerns.

`Admin::EditorResource` (`app/controllers/concerns/admin/editor_resource.rb`) is a shared concern for the three editor-backed admin controllers (`Admin::PostsController`, `Admin::PagesController`, `Admin::NewslettersController`). It sets `layout :choose_layout` (editor layout on `new`/`edit`/`create`/`update`, `"admin"` elsewhere — declared per-controller via `uses_editor_layout "admin_editor"` etc.) and provides `respond_with_saved(record, notice:, status:)` / `respond_with_errors(record, template)` for the shared HTML+JSON `respond_to` branches on `create`/`update`. Including controllers implement `resource_json(record)` and `edit_path_for(record)` to supply their resource-specific JSON payload and redirect target; anything else that differs (e.g. `Post#create_version_if_needed!` after update) stays in the controller.

`Admin::CrudResource` (`app/controllers/concerns/admin/crud_resource.rb`) supplies `new`/`create`/`edit`/`update`/`destroy` for the plain admin resources (categories, mailing lists, subscriber labels, membership tiers, segments, webhooks). A controller includes it, calls `crud_resource Model` (options: `as:` for the view ivar name, e.g. `@tier`/`@label`; `flash_scope:`, default `flash.admin.<plural>`; `member_actions:` for extra actions that need the record loaded) and defines private `resource_params`. It redirects to the resource's index (`after_save_path`). The exceptions are overrides: categories' `find_resource` looks up by slug, tiers override `new` (default currency) and `destroy` (refused while it has members), webhooks override `new`, `create` (`super { flash[:raw_secret] = ... }`) and `after_save_path` (a new webhook goes to its edit page). A webhooks-style `before_action` that must run before the record loads is declared above `crud_resource`.

The editor's two oEmbed attachment controllers (`Admin::XPostsController`, `Admin::YouTubeVideosController`) share `create` through `Admin::OembedEmbeddable`; each defines only `embed_class` and `embed_error_message` (the fallback when there are no validation errors to report).

Index status filters go through `Admin::BaseController#filter_by_status(scope, allowed, value: params[:status])`, which applies the named model scope only for whitelisted values (a Hash maps a param value to a differently named scope, as comments' `pending` does). Never pass a status param straight to `where`. API token visibility (admins see all, writers their own) is `ApiToken.visible_to(user)`.

### Service Layer
- **Form Objects** for multi-model input (e.g., `Registration`)
- **Service Objects** in `app/services/` for business operations (e.g., `Ai::SystemPrompts`, `Ai::PostContextBuilder`, `Ai::ImagePromptSuggester`, `MarkdownRenderer`, `Mcp::Tools::*`)
- **Query Objects** in `app/queries/` for complex queries (e.g., `PostViewsQuery`, `SubscriberGrowthQuery`, `PostEngagementQuery`, `ReferrerAnalyticsQuery`, `SegmentSubscribersQuery`)

### Internationalization (i18n)
Site-wide locale configured via `SiteSetting.locale` (default: `"en"`). The `SiteSetting::Localization` concern defines `SUPPORTED_LOCALES` and validates the locale value. `ApplicationController` sets `I18n.locale` from the site setting on every request. All UI strings live in `config/locales/en.yml` and `config/locales/es.yml`. To add a new locale: add the language code to `SUPPORTED_LOCALES` in `app/models/site_setting/localization.rb`, add it to `config.i18n.available_locales` in `config/application.rb`, and create the corresponding YAML file in `config/locales/`.

Dates and times are rendered via `l(value, format: :short|:long|:with_time)`, never `strftime`, so they follow the site locale. Named formats live under `date.formats`/`time.formats` in each locale file — `date.formats` (`short`, `long`) for date-only values and `time.formats` (`short`, `long`, `with_time`) for values that include a time of day. Because there's no `rails-i18n` gem, each locale file also defines its own `date.month_names`/`abbr_month_names`/`day_names`/`abbr_day_names` and `time.am`/`pm` — without these, `%B`/`%A`/`%p` in a format string raise `I18n::MissingTranslationData` for any locale ActiveSupport doesn't ship a default for (i.e. anything but English). **`l` dispatches on the argument's class**: a `Date` uses `date.formats`, while a `Time`/`ActiveSupport::TimeWithZone` uses `time.formats` — so a date-only display of a timestamp column (`created_at`, `published_at`, etc.) must call `l(value.to_date, format: :short)`, not `l(value, format: :short)`, or it silently pulls from `time.formats` instead. `ApplicationHelper#published_on(record, **html_options)` wraps this for the `<time datetime="...">` tag used by post card partials (`posts/_post`, `posts/_related_posts`, `posts/show`, `admin/posts/_preview`).

### Background Jobs
Solid Queue (database-backed). Jobs organized by domain in `app/jobs/`. Recurring tasks configured in `config/recurring.yml`. **Solid Queue loads only the block named after `Rails.env` when one exists** (it does not merge top-level tasks into it), so tasks every environment needs go under the `default: &default` anchor that each environment block merges with `<<: *default`; production-only tasks sit in the `production:` block beside the merge. A task added at the top level would silently never run in production.

Fan-outs are bulk-enqueued, never one `perform_later` per record: build the instances and call `ActiveJob.perform_all_later` (`ActionMailer.deliver_all_later` for mail), one call per batch (`SendPostNotificationsJob` and `FederatePostJob` use batches of 500, `SendDigestsJob` one per subscriber batch, `WebhookDispatcher` one per event). Bulk enqueueing **skips enqueue callbacks**, so don't add `before_enqueue`/`around_enqueue` behavior to these jobs. Tests assert on batching with `BulkEnqueueHelper#capture_bulk_enqueues`.

`PublishScheduledPostsJob` and `SendScheduledNewslettersJob` rescue per record and report with `Rails.error.report`, so one record that raises can't block the rest of the run (it is retried on the next one).

### SiteSetting Caching
`SiteSetting.current` is memoized on `Current.site_setting` (`app/models/current.rb`) for the lifetime of a request or job — `first_or_create!` only runs once per request instead of on every call. An `after_commit` callback on `SiteSetting` clears the memoized value so an update within the same request is not stale. `SiteHelper` exposes a `site_setting` helper method that views should call instead of `SiteSetting.current` directly. `Newsletter::Templatable#resolved_*` methods accept an optional `site` argument so `email_settings` can pass down a single fetched record rather than re-querying per field.

### Admin Settings & Masked Secrets
`Admin::SettingsController` and `Admin::NewsletterSettingsController` share their `edit`/`update` actions via the `Admin::SiteSettingsResource` concern (`app/controllers/concerns/admin/site_settings_resource.rb`); each controller only defines `site_setting_params`, `redirect_path`, and `notice_key`. The `SiteSetting::MaskedSecrets` concern (`app/models/site_setting/masked_secrets.rb`) owns the "••••••••" placeholder mask for encrypted keys (`SECRET_ATTRIBUTES`): `assign_attributes_ignoring_mask(attrs)` drops any secret attribute whose submitted value is still the mask (leaving the stored key unchanged), while a blank value still clears it; `masked_value_for(attribute)` is what views call to render the mask (or "") for a password field's current value.

### AI Integration
Uses the **RubyLLM** gem for a unified LLM interface across providers (Claude for text, Gemini/OpenAI for images). API keys are stored with Active Record Encryption on `SiteSetting` — key presence enables a feature, `nil` disables it (no separate toggle). `Ai::Client` (`app/services/ai/client.rb`) is the single place that calls `RubyLLM.configure` — `configure!(settings)` sets all three provider keys, `chat(settings)` configures and returns a `RubyLLM.chat(model: settings.ai_model_name)`, and `paint(prompt, settings)` configures and delegates to `RubyLLM.paint`. `Ai::Configurable#configure_ruby_llm!` and `AiResponseJob`/`GenerateFeaturedImageJob`/`Admin::Ai::FeaturedImagesController` all delegate to it instead of building their own `RubyLLM.configure` block. `configure_ruby_llm!` runs as a `before_action` only on `Admin::Ai::BaseController` (and subclasses) — not on `Admin::BaseController` — so non-AI admin pages don't decrypt AI API keys on every request. AI controllers are nested under `admin/posts/:id/ai/` and streaming responses use Turbo Streams + Solid Cable (`AiResponseJob` broadcasts the reply in batches: every broadcast is a Solid Cable insert on SQLite, so chunks are buffered until `STREAM_FLUSH_INTERVAL` or `STREAM_FLUSH_SIZE` is reached, with a final flush, and HTML-escaped because Turbo inserts them as markup). `Ai::SystemPrompts.for(quick_action, context)` picks the system prompt from its `QUICK_ACTIONS` map, falling back to `chat`. `AiResponseJob` precomputes the latest user message id once before replaying chat history, rather than re-querying it per message in the loop.

Only `Chat` and `Message` are application models (`acts_as_chat` / `acts_as_message`). The model registry, tool calls and usage ledger are RubyLLM's own `ruby_llm_*` tables. `bin/docker-entrypoint` runs `ruby_llm:load_models` on boot so a stored registry can't fall behind the gem. `Ai::Client.paint` passes `provider:` and `assume_model_exists: true` so image generation doesn't depend on the registry listing an id, or resolve it to another provider. When a provider retires a model, replace it in `SiteSetting::AiConfiguration`'s `AI_MODELS`/`IMAGE_MODELS` (first entry = default, also mirrored in the `site_settings` column defaults and `config/initializers/ruby_llm.rb`) and add a data migration that moves saved settings onto the replacement, as `ReplaceRetiredAiModels` does. `RubyLLM::ModelNotFoundError` is not a `RubyLLM::Error`, so rescue both around chat calls.

### Custom Static Pages
Pages (`Page` model) provide custom static content at top-level URLs (`/:slug`). The catch-all route **must remain last** in `config/routes.rb` (after admin namespace and health check) to avoid intercepting other routes. Pages use `admin_page_editor` layout (simplified editor without AI/preview). Reserved slugs (admin, posts, feed, etc.) are validated at the model level. Pages are **not** added to the site menu automatically — link them from Navigation (below).

### Navigation Menus
`NavigationItem` (`label`, `url`, `location` enum `header`/`footer`/`social` with `validate: true`, `position`, `open_in_new_tab`) is the single source of the public site's menus — the header nav (`layouts/shared/_header_nav`), footer text links, and footer social icons (`layouts/shared/_footer`). There is no hardcoded "Home" link and no per-page "show in navigation" flag; the `CreateNavigationItems` migration converted the old `pages.show_in_navigation`/`pages.position` columns (since dropped) into header items. URLs must be an internal path starting with a single `/`, an `http(s)` URL, or `mailto:` (social items: `http(s)` only) — this validation is what keeps `javascript:` hrefs out of the layout, so don't loosen it. New items (and items moved to another location) are appended via `before_save`; `NavigationItem.reposition!(location, ids)` rewrites positions for drag-and-drop and `#move(:up/:down)` is the keyboard/no-JS fallback.

`NavigationItem.for_location(location)` is what views call — it caches each location's ordered records in `Rails.cache` (Solid Cache in production; `null_store` in test, so cache tests swap in a `MemoryStore`), and `after_commit` plus `reposition!` (which uses `update_columns`) expire all locations. Bump `NavigationItem::Cacheable::CACHE_VERSION` if the cached records' shape changes. `NavigationItem::SocialPlatform#social_platform` maps the URL host to a platform (unknown hosts → `:website`, `/@user` paths → `:mastodon`), and `NavigationHelper#social_icon(platform)` renders the matching Simple Icons (CC0) SVG from `NavigationHelper::SOCIAL_ICONS`; `navigation_link(item)` adds `target="_blank" rel="noopener noreferrer"` when `open_in_new_tab`.

Admin UI is `Admin::NavigationItemsController` at `/admin/navigation` (admin role only; linked from the sidebar and Settings): one page with a section per location, inline add forms, and a generic `sortable` Stimulus controller (native HTML5 drag-and-drop within one list, PATCHes `{ location, ids }` to `reorder`, reloads the page if that fails). Up/down arrows hide at list edges via Tailwind `group-first/item`/`group-last/item`, so they stay correct after a drag without a re-render. The JSON export includes `navigation_items`.

### Post Editor
Uses the `admin_editor` layout. Autosave triggers on a 3-second debounce, serializing `#post_form` FormData. The editor drawer is a tabbed panel (AI + Settings + Versions). Settings fields use `form="post_form"` attribute with event listeners on the settings tab container to trigger autosave.

### Editor Layout Composition
`admin_editor`, `admin_page_editor`, and `newsletter_editor` are thin compositions of shared partials in `app/views/layouts/editor/`: `_head` (`default_title:`, `fonts: true` — newsletter editor passes `fonts: false` to skip `font_stylesheet_tags`/`typography_style_tag`), `_top_bar` (`back_label:`), `_overlay`, and `_discard_modal` (`title:`, `message:`; the "Keep editing"/"Discard" button labels are shared under `layouts.editor.*` in the locale files rather than duplicated per layout). Flash messages across all six layouts (three editors, `admin`, `admin_auth`, and the public `application` layout) render through `layouts/shared/_flash` (`variant: :editor | :admin | :auth | :public`, default `:editor`) so `notice`/`alert` markup lives in one place; the public variant uses the `.flash`/`.flash--notice`/`.flash--alert` BEM classes in `app/assets/tailwind/components/_flash.css`. `Admin::PostsController` sets `@chat` via a `set_chat` before_action (on `edit`/`update`, when `SiteSetting.current.ai_configured?`) rather than the layout performing the `Chat.find_or_create_for` lookup/write itself.

`editor_drawer_controller.js` owns only drawer chrome — open/close, pin (persisted through `lib/storage.js`), tab switching, Escape, and Cmd/Ctrl+Shift+A. It carries no AI-specific targets or values: it derives whether an AI tab exists from the presence of a `data-tab="ai"` tab button, and `showTab` dispatches `editor-drawer:tab-shown` (with `{ tab }`) **on the panel target**, so controllers mounted inside the panel can react. `ai_chat_controller.js` owns AI chat transport (send, quick actions, clear conversation, Enter-to-send, scroll-to-bottom) and is mounted on the panel root in `admin/posts/_editor_panel.html.erb` only when `ai_available` — the page and newsletter editors render their own panels and never load it. It POSTs to `/admin/posts/:slug/ai/messages` via `requestTurboStream` (from `lib/request.js`) rather than building a hidden `<form>`, and reads title/subtitle from the autosave controller's form (`formSelectorValue`) instead of a document-wide `querySelector`.

### Post Content & Search Indexing
`Post#body_plain` is the canonical plain-text source for a post's content — `Post#excerpt(length)` truncates it and is used by `seo_description`, the featured-post teaser, and the gated-content teaser. Never re-derive plain text from `content.to_plain_text` outside of `Post::Searchable#update_body_plain`; that callback only recomputes `body_plain` when `content` actually changed (`before_save :update_body_plain, if: -> { new_record? || content.changed? }`), so a settings-only save (autosave, love counter, status toggle) skips the Nokogiri parse. `calculate_reading_time` is similarly guarded with `will_save_change_to_body_plain?`. The `posts_fts_update` SQLite trigger has a `WHEN` clause so the FTS5 row is only deleted/reinserted when `title`, `subtitle`, or `body_plain` actually changed. Run `rake posts:backfill_body_plain` to populate `body_plain` for posts created before the column existed.

The FTS5 body snippets shown on public search results quote post text, so `PostsController#index` keeps a snippet only for posts the reader can view (`can_view_post?`); don't pass `Post.search_with_snippets` results to a view unfiltered. The snippet is part of the post-card cache key (see Post Cards below), which is what keeps a member's card from being served to anonymous readers.

### Post Cards & Listing Pagination
Post cards (`posts/_post`) are only rendered through `PostCardsHelper#render_post_cards(posts, snippets: {}, **options)`, never with `render "posts/post"` in a loop: it renders a collection with a `cached:` lambda, so a listing's cards are fetched with one `read_multi` (one Solid Cache query) instead of a read per card, and the partial has no `cache` block of its own. Collection caching keys **only** on the lambda's value, not on the locals, so `post_card_cache_key` is built from `PostCardsHelper::POST_CARD_OPTIONS` (every display option and its default) plus the post, author identity, category, search `body_snippet` and `I18n.locale`; `render_post_cards` rejects an option missing from that list. Add a new card option there, never as a bare partial local, or two different cards will share one cache entry. The partial's strict locals have no defaults for the same reason. `snippets` maps post id → search result; pass only what `PostsController#viewable_snippets` allowed.

The home page, category, tag and signed-in `/reading-list` pages are paginated with `Paginatable#paginate` (10 per page) and infinite scroll: `posts/_post_page` (`posts:`, `page:`, `next_page:`, `next_page_path:`, optional `snippets:`/`card:` options) renders one `posts_page_<n>` turbo frame plus a lazy frame for the next page. `Paginatable#post_page_frame_request?` detects that frame request; category, tag and reading-list actions answer it with `render layout: false` of the full template (Turbo keeps only the matching frame), while `PostsController#index` renders the `_post_page` partial directly to skip the featured hero. Author pages keep their "Load more" link. The anonymous reading list (`ReadingListPostsController`, up to `ReadingListItem::MAX_ITEMS` ids) is not paginated. The sitemap selects only `slug`/`updated_at`.

### Post Versioning
`PostVersion` stores full snapshots (title, subtitle, content HTML, body plain text) on each save. Auto-versioning triggers on update with a 5-minute cooldown (`Post::Versionable`). Manual "Save version" button in the editor drawer's Versions tab. Diff view uses the `diffy` gem for plain-text comparison. "Restore" replaces the post's current content. Max 50 versions per post, pruned inline on version creation. Admin CRUD at `/admin/posts/:id/post_versions`.

### Post Status Transitions
`Post::Notifiable`, `Post::Webhookable` and `Post::Federatable` all react to status changes from `after_commit on: [:create, :update]`, using the shared predicates on `Post::Publishable`: `became_published?`, `became_scheduled?`, `left_published?` (the status before the last save was published) and `edited_while_published?` (no status change, published, and `revised?`). On create the "before" status is the column default (draft), so creating a post already published behaves exactly like publishing a draft: one email, one `post.published` webhook, one fediverse `Create`. Use these predicates rather than re-deriving transitions from `saved_change_to_status?` in a new concern.

### Post Revisions (Coalesced Updates)
`Post::Revisable` stamps `posts.revised_at` in a `before_save` whenever a save changes something readers and integrations see: `REVISED_ATTRIBUTES` (title, subtitle, slug, body_plain, visibility, published_at, meta_description). Settings-only saves (featured, show_toc, category) and counter bumps move `updated_at` but not `revised_at`. It's included right after `Post::Searchable` so a content change has already reached `body_plain`. `Post::Webhookable` and `Post::Federatable` enqueue their "updated" notification (`PostUpdatedWebhookJob`, `FederatePostJob("update")`) only when `revised?`, delayed by `Post::Revisable::UPDATE_DELAY` (2 minutes) and carrying `revised_at.to_f`; the job skips itself when `post.revised_since?(revision)`, so autosave every 3 seconds yields one notification per burst. Coalescing on `revised_at` rather than `updated_at` is deliberate: a settings-only save after an edit would otherwise make the edit's job skip with no newer job queued.

### RSS Feed
`/feed` is anonymous, so `feeds/index.xml.builder` puts the full body in `content:encoded` only for `visibility_public?` posts; members-only and paid posts get `seo_description` plus a "read the full post" link, matching `ActivityPub::ArticleSerializer`. Never emit `post.content` to an unauthenticated surface without that check.

### SEO Head Tags
`MetaTagsHelper#seo_head_tags(title:, description:, url:, type:, image:, extra_tags:, json_ld:)` emits a page's whole SEO `<head>` sequence — description meta, Open Graph group, `extra_tags`, Twitter card group, canonical link, optional JSON-LD — in that fixed order. Every public page view calls it once instead of chaining `meta_description_tag` / `open_graph_tags` / `twitter_card_tags` / `canonical_tag` / `json_ld_tag`; `meta_tags_for_post` is a thin wrapper that passes the post's `article:*` metadata through `extra_tags` (which is why the slot sits between the OG and Twitter groups). The image is resolved once per call and shared by both the OG and Twitter groups.

The helpers are split by responsibility: `MetaTagsHelper` (page title + meta/OG/Twitter/canonical tags), `StructuredDataHelper` (`json_ld_tag`, `json_ld_for_post`, `json_ld_for_author`, `json_ld_breadcrumb_list`), and `BreadcrumbsHelper` (`breadcrumb_items`, `breadcrumb_navigation`). `breadcrumb_items` returns `{name:, path:, url:}` entries and is the single source for both the visible breadcrumb nav (uses `:path`) and the BreadcrumbList JSON-LD (uses `:url`); the last entry has neither because it is the current page. Rails includes all helpers in views automatically, but helper *tests* must `include` each module they reach into (e.g. `StructuredDataHelperTest` includes `BreadcrumbsHelper` and `ImageOptimizationHelper`).

Image URLs are memoized for the request: `SiteHelper#default_og_image_url` uses a `defined?` guard so a nil result (no OG image configured) isn't recomputed, and `ImageOptimizationHelper#post_og_image_url(post)` caches `optimized_og_image_url` per post id so the head tags and the Article JSON-LD share one variant lookup. `Post#seo_description` and `Page#seo_description` are memoized for the same reason — a page renders them three or four times.

### JavaScript Entry Points
There are two importmap entry points. `application` (`app/javascript/application.js`: Turbo plus `controllers/index.js`, which eager-loads `app/javascript/controllers/`) is all the public layout loads (`javascript_importmap_tags`). `admin` (`app/javascript/admin/index.js`) imports `application`, then `lexxy`, then eager-loads `app/javascript/admin/controllers/`; `layouts/admin`, `layouts/admin_auth` and `layouts/editor/_head` load it with `javascript_importmap_tags "admin"`. **Put a controller in `app/javascript/controllers/` only if a public view uses it** (it then works on admin pages too); admin-only controllers go in `app/javascript/admin/controllers/`, and admin-only helpers in `app/javascript/admin/lib/` (imported as `admin/lib/<name>`). ### Shared JS Modules
`app/javascript/lib/` holds framework-agnostic helpers shared across Stimulus controllers (pinned via `pin_all_from "app/javascript/lib", under: "lib"` in `config/importmap.rb`, imported as `lib/<name>`). Helpers only admin controllers use live in `app/javascript/admin/lib/` instead (`click_outside`, `listbox`, `svg_chart`, `action_text`, imported as `admin/lib/<name>`), so public pages don't preload them.

`lib/request.js` centralizes the CSRF-token meta lookup and the three fetch idioms used throughout the app: `request(url, opts)` (sets `X-CSRF-Token`, JSON-encodes a plain object body, form-encodes a `URLSearchParams` body, passes `FormData` through untouched), `requestJSON(url, opts)` (parses the JSON response and throws with `data.error` when the response isn't ok), and `requestTurboStream(url, opts)` (sets the Turbo Stream `Accept` header and renders the response via `Turbo.renderStreamMessage`). Controllers that POST or fetch should use these helpers instead of duplicating the CSRF meta-tag lookup.

`lib/dom.js` holds `escapeHtml(str)` (the single HTML-escaping implementation in the app — `lib/markdown.js`, `custom_select` and anything else interpolating untrusted text into a template literal import it rather than rolling their own) and `capitalize(str)` (used to build Stimulus `has<Name>Target` property names in `email_branding_preview`).

`admin/lib/click_outside.js` exposes `useClickOutside(controller, { onClickOutside })`, which returns `{ observe, unobserve }` instead of registering immediately. Dropdown controllers call `observe()` in `open()` and `unobserve()` in `close()` and `disconnect()`, so a `document` click listener only exists while a dropdown is actually open.

`admin/lib/listbox.js` provides `ListboxNavigator`, the shared Up/Down/Home/End/Enter/Space/Escape (plus optional type-ahead) handling for `tag_select` and `custom_select`. It owns only the highlighted index; everything visual or app-specific is injected — `getItems`, `highlight(item, on)`, `onSelect(item)`, `onEscape(event)`, `clearHighlight`, `isOpen`/`onOpenRequest`, `getItemText`, and the `typeAhead`/`homeEnd`/`selectOnSpace` flags. `handleKeydown(event)` returns whether it handled the key, so callers can fall through to their own (e.g. `tag_select`'s Backspace-removes-last-pill). **Both selects bind keydown to `this.element`, not `document`, and call `stopPropagation()` on Escape** — that is what lets the first Escape close an open dropdown and only the next one reach `editor_drawer`'s document-level handler and close the drawer. Do not move either listener back to `document`; the drawer no longer probes for open dropdowns in the DOM.

`app/views/shared/_tag_select.html.erb` keeps the pill, option, and checkmark markup in `<template>` elements (`pillTemplate`, `optionTemplate`, `checkmarkTemplate`) that `tag_select_controller` clones, so the styling lives in one place and the controller sets text via `textContent` instead of building HTML strings.

`admin/lib/svg_chart.js` is the shared renderer for all hand-rolled SVG charts (no external charting library) — `svgEl(name, attrs, text)` builds namespaced SVG elements, `renderBarChart(container, entries, opts)` draws gridlines/bars/x-labels for `growth_chart` and `traffic_chart` (which differ only in `minBarWidth`, `labelInterval`, and label formatter — `formatMonthLabel`/`formatDayLabel`), and `renderSparkline(container, values, opts)` draws the dashboard's line+area sparkline (`chart_controller`). All three controllers render into a persistent container element via `container.replaceChildren(...)`, so redrawing (e.g. on data change) doesn't destroy the target. The growth chart's Monthly/Cumulative toggle uses Stimulus `static classes` (`data-growth-chart-active-class` / `-inactive-class`) with `classList.add/remove` rather than string replacement on `className`.

`lib/timers.js` keeps Stimulus timers tied to the controller lifecycle — an untracked `setTimeout` survives `disconnect()` and keeps firing against a detached controller after a Turbo navigation. `debounce(fn, ms)` returns a wrapped function with a `.cancel()` method (used by `handle_check`); `useTimeouts()` returns `{ set, clear, clearAll }` that tracks every timeout id so `disconnect()` can `clearAll()` (used by `autosave` and `custom_select`). `autosave` also keeps a `connected` flag so a response landing after disconnect can't queue a new retry, which is what made a failed save loop forever after navigating away.

`lib/storage.js` exports a `storage` object (`get`/`set`/`remove`/`getBoolean`) wrapping `localStorage` in try/catch — the API throws outright in private-browsing/blocked-site-data configurations, and an unguarded read inside `connect()` aborts the whole controller. `editor_drawer` and `theme_toggle` go through it; the inline theme boot script in `layouts/application.html.erb` has its own try/catch since it runs before the module graph loads. The `theme` key name is shared between that script and `theme_toggle`, so don't rename it.

### Email & Payment Provider Adapters
`EmailService` and `PaymentService` each follow the same provider pattern: a module-level `.provider` factory builds the configured adapter from `SiteSetting` (injecting keys/secrets into the constructor rather than having the adapter read `SiteSetting` itself), and `.configured?` reports whether the feature is usable. Both adapter interfaces are declared on a `Base` class (`EmailService::Base`, `PaymentService::Base`) that the concrete adapters subclass. `EmailService::Base#deliver_newsletter(newsletter, subscriber)` is the single entry point callers use — `SendNewsletterJob` always calls `provider.deliver_newsletter`, with no provider branching in the job. `deliver_newsletter` is synchronous and must raise when the provider did not accept the message: `EmailService::Smtp#deliver_newsletter` delivers `NewsletterMailer#campaign` with `deliver_now` (forcing `raise_delivery_errors` on that message), and `EmailService::Sendgrid#deliver_newsletter` renders that same mailer and posts it via the SendGrid API (`#send_email`, one memoized API client per adapter instance), raising `EmailService::DeliveryError` on a non-2xx response.

`SendNewsletterJob` delivers at-least-once. It walks the subscribers with no `NewsletterDelivery` row and writes that row (one `insert` per recipient, `unique_by` the newsletter/subscriber index) only **after** `deliver_newsletter` returns, so a row means "the provider accepted it". A provider error for one subscriber is logged and the loop continues (a run stops early after `MAX_CONSECUTIVE_FAILURES` rejections in a row); if anyone failed the job raises `PartialDeliveryError`, and `retry_on` (`MAX_ATTEMPTS` = 5, polynomial backoff) reruns it from the still-undelivered subscribers, so nobody delivered is sent to again. The one duplicate window is a crash between the provider accepting and the row being written. When retries run out the newsletter is still marked sent. `Newsletter#mark_sent!` defaults `recipients_count` to the deliveries recorded across every run. The job returns at once unless the newsletter is `sending`, and `limits_concurrency` keeps two runs for one newsletter from overlapping. SendGrid webhook event processing (updating `NewsletterDelivery` open/click/bounce/unsubscribe state) lives in `EmailService::Sendgrid::WebhookProcessor`, used directly by `Webhooks::SendgridController` — it needs no API key, since it never calls the SendGrid API. Open/click events are written with SQL (`update_all`), never read-modify-write, so concurrent events don't lose increments. `PaymentService::Stripe` is constructed with `secret_key:`, `publishable_key:`, and `webhook_secret:` all injected by `PaymentService.provider` from `SiteSetting`, so `construct_webhook_event` never reads `SiteSetting` directly. `EmailService.from_address` is the single `SMTP_FROM` env lookup, used by both `ApplicationMailer`'s default `from` and `EmailService::Sendgrid`.

### Email Frequency & Digests
`Subscriber::EmailPreferences` adds `email_frequency` (enum `immediate`/`weekly`/`monthly`/`none`, `prefix: :email`, `validate: true`, default `immediate`). The frequency governs **post emails only**: `SendPostNotificationsJob` sends to `post.notification_recipients.email_immediate`, and `SendDigestsJob` covers `weekly`/`monthly`. Newsletters ignore it (`Newsletter::Sendable#target_subscribers` is unchanged), so `none` means "no post emails", not unsubscribed.

`SendDigestsJob.perform(frequency)` runs from `config/recurring.yml` (`"0 8 * * 1"` weekly, `"0 8 1 * *"` monthly, server time zone). `subscribers.last_digest_at` is a **delivery cursor**, meaning "posts published before this have reached the subscriber", not strictly "when a digest was last sent". `#digest_window_start(now)` is `last_digest_at || now - period`. The job lists `Post.live.where(published_at: since...now)` (half-open, so consecutive windows neither overlap nor gap) limited to posts on the subscriber's active mailing lists (subscribers on no active list are skipped and keep their cursor), caches the lookup per distinct (window start, list ids) pair, builds a `DigestMailer.digest(subscriber, post_ids.first(POST_LIMIT), total_count)`, then, per batch, bulk-enqueues those digests and `update_all`s `last_digest_at` to the run's `now`. A retried run therefore finds empty windows, and a subscriber with no new posts keeps their cursor. A `before_save` moves the cursor when the frequency changes: from `immediate` it jumps to now (those posts were already emailed individually), from `none` it clears (falls back to the last period), and between `weekly` and `monthly` it is kept. `DigestMailer` reloads `Post.live` at delivery time and returns without mailing if the subscriber has since unsubscribed or every post was unpublished. It shows `seo_description` as the excerpt (already public in meta tags, so it doesn't leak gated content beyond what the page head does), and uses a non-WebP featured-image variant because email clients can't render WebP.

Subscribers manage the setting at `/email-preferences` (`EmailPreferencesController`; `email-preferences` is a reserved `Page` slug). Access is either a signed `token` param (`Subscriber#email_preferences_token` / `.find_by_email_preferences_token`, message verifier purpose `"email_preferences"`, 30-day expiry, separate from the `"unsubscribe"` token) or a signed-in `current_subscriber`. `PostNotificationMailer`, `DigestMailer` and `NewsletterMailer` set `@email_preferences_url`, which `mailer/_footer` renders beside the unsubscribe link, and the unsubscribe confirmation page links to it as an alternative. In mailer templates build post links with `post_url(slug: post.slug)`: `post_url(post, slug: ...)` puts the record in the `:format` slot and yields `/posts/<slug>.<slug>`.

### Mailing Lists (Multiple Newsletters)
`MailingList` is the subscribable list readers see as a "newsletter" — **not** `Newsletter`, which is a one-off email campaign (the name was taken by #22). API/MCP don't accept list ids yet, so posts created there use the default lists.

The `CreateMailingLists` migration folds existing installs into one default "Newsletter" list (every non-unsubscribed subscriber, every post) and stamps published posts as notified. The JSON export includes `mailing_lists` and `mailing_list_ids` on posts and subscribers.

### Paid Memberships (Stripe)
Prose supports Ghost-style paid memberships with Stripe integration. Feature is gated — UI only appears when Stripe keys are configured in `SiteSetting`. Direct Stripe API keys (not Stripe Connect), stored encrypted like AI keys. 3-level post visibility: `public` (default), `members_only` (free sign-in), `paid_only` (subscription required). `PaymentService::Stripe` handles checkout sessions, billing portal, subscriptions, and webhook event construction — see Email & Payment Provider Adapters above. `StripeWebhookJob` processes checkout completions, subscription updates/deletions, and payment failures (idempotent) — it's a thin dispatcher that delegates status mapping and attribute syncing to `Membership::StripeSyncable`. `SyncStripeSubscriptionJob` runs daily to keep membership status in sync, also via `StripeSyncable`. Admin controllers at `/admin/payment_settings`, `/admin/membership_tiers`, `/admin/memberships`, `/admin/revenue`. Public pricing page at `/memberships`. Content gating in `posts/show` — `PostsController` sets `@can_view` via `MembershipAccess` concern. Query objects: `RevenueQuery` (MRR, ARR, churn) and `MembershipGrowthQuery` (new/canceled/net by month).

`PaymentGating` (`app/controllers/concerns/payment_gating.rb`), included on `ApplicationController`, is the single source of Stripe-configuration gating: `helper_method :payments_configured?` (memoized per request via a `defined?(@payments_configured)` guard, mirroring `SiteHelper#default_og_image_url`) replaces direct `PaymentService.configured?` calls in views (`posts/_paywall`, `layouts/_admin_sidebar_content`, `admin/membership_tiers/_tier_row`/`_tier_card`), and `require_payments_configured(redirect_to: root_path, alert: nil)` is a `before_action` that redirects when Stripe isn't configured — `MembershipsController` uses the default (silent redirect to `root_path`), while `Admin::RevenueController` overrides it to call `super(redirect_to: admin_root_path, alert: t("flash.payments.not_configured"))`. `Admin::MembershipTiersController` and `Admin::MembershipsController` are deliberately left ungated — tiers must be manageable before their first Stripe sync, and comp memberships (`Membership.grant_complimentary!`) don't require Stripe at all.

`Membership::StripeSyncable` centralizes the Stripe→Membership mapping shared by both jobs: `Membership.status_from_stripe(stripe_status)` maps a Stripe subscription status string to the `status` enum (unknown statuses fall back to `:incomplete`); `#sync_from_stripe!(subscription)` accepts either a `Stripe::Subscription` object or a string-keyed Hash (webhook payload) and updates `status`/`current_period_start`/`current_period_end`/`canceled_at` — missing period fields leave the stored value untouched, while `canceled_at` always reflects the given value (including clearing it back to `nil`) since Stripe always sends that field on a full subscription object; `Membership.activate_from_checkout!(session_data, subscription)` handles `checkout.session.completed` — looks up the subscriber by email and the tier by Stripe price ID, then `find_or_create_by!`s the membership (idempotent against duplicate webhook delivery) before calling `sync_from_stripe!`.

`Membership.grant_complimentary!(subscriber:, membership_tier:)` creates a Stripe-free active membership (100-year period) for admin-granted comps. It's invoked from the subscriber show page via `POST /admin/subscribers/:subscriber_id/memberships/comp` (`admin_subscriber_comp_membership_path`, routed to `Admin::MembershipsController#comp`) rather than a member route on `admin/memberships`, since granting a comp creates a new membership and doesn't operate on an existing one.

`MembershipTier::Syncable` runs Stripe product/price creation `after_commit` (not `after_save`) via `SyncMembershipTierJob`, so the HTTP round-trip to Stripe never holds SQLite's single writer lock open during the save transaction. The admin tiers index (`app/views/admin/membership_tiers/index.html.erb`) shows a "Syncing…" badge on any tier missing a `stripe_price_id` and subscribes to a `"membership_tiers"` Turbo Stream; `SyncMembershipTierJob` broadcasts a `broadcast_replace_to` for both the tier's mobile card and desktop row partials once the sync completes, so the badge clears without a page reload.

### Reading List (Bookmarks)
Readers save posts for later with the bookmark icon rendered by `ReadingListHelper#bookmark_button` in every post card's meta row (`posts/_post`) and on `posts/show`, and view them at `/reading-list` (`ReadingListController#show`, also linked from the masthead icon group `.masthead__actions`; `reading-list` is a reserved `Page` slug). `ReadingListItem` belongs to `Identity` (like `Love`/`Comment`), so staff users signed into the public site get a list too.

### MCP Server (Model Context Protocol)
Prose exposes an MCP endpoint at `POST /mcp` for AI assistants to manage blog content. See `docs/mcp_setup.md` for the full client setup guide.

**Authentication**: Bearer token via `Authorization` header. Tokens are prefixed with `prose_`, stored as SHA256 digests (never raw), and support instant revocation. The `ApiToken` model handles generation, lookup, and usage tracking (last used time/IP). The `User::ApiTokenable` concern adds `has_many :api_tokens` and a convenience `generate_api_token!` method.

**Controller**: `Mcp::SessionsController` (inherits `ActionController::API`) — one `handle` action routed for `GET`/`POST`/`DELETE /mcp` that authenticates the token, sets `Current.user`, and hands the request to the gem's `MCP::Server::Transports::StreamableHTTPTransport` (built per request with `stateless: true, enable_json_response: true`, returning a Rack triple the action renders). Always go through the transport, never `MCP::Server#handle_json` directly. The transport handles the Streamable HTTP rules that real clients depend on: `202` for notifications, `405` for `GET` (no SSE stream), Accept/Content-Type validation, the `MCP-Protocol-Version` header, and the 2026-07-28 per-request envelope. Claude Desktop reaches it through the `mcp-remote` stdio bridge, since `claude_desktop_config.json` can't send a bearer header to a remote URL. Clients (and tests) must send `Content-Type: application/json` plus `Accept: application/json, text/event-stream`. `wrap_parameters false` keeps Rails from parsing the body so the transport returns its own JSON-RPC parse error, and `MAX_REQUEST_BYTES` (16 MB) raises the transport's 4 MiB default for base64 uploads. DNS-rebinding checks are disabled in favor of Rails `config.hosts`. Rate limited at 60 req/min per IP.

**Tool architecture**: 14 tools in `app/services/mcp/tools/`, all inheriting from `Mcp::Tools::Base` (itself an `MCP::Tool` subclass). Each declares a `description`, `input_schema`, and `call(server_context:, **params)` class method. Tools are registered via `Mcp::ToolRegistry.all`, which excludes `Base`. `Base` provides private class-level helpers shared across tools: `with_post` (wraps `find_post` with a `"Post not found: ..."` error envelope on `ActiveRecord::RecordNotFound`) and `success`/`failure` response envelope builders. The lookups themselves — `find_post` (slug-or-numeric-ID), `find_category`, `find_tag`, `find_or_create_tags`, `decode_upload` (base64 → `[StringIO, content_type]`) — live in `Mcp::ContentLookup` (`app/services/mcp/content_lookup.rb`), included into `Base`'s singleton class and into `Api::V1::BaseController`, so MCP and REST share one implementation. `MCP::Tool.inherited` resets description/schema per subclass and `tool_name` derives from the leaf class name, so the intermediate `Base` class doesn't affect tool names or schemas.

### REST API
A versioned JSON REST API lives alongside MCP at `/api/v1/` for non-MCP integrations (mobile apps, custom frontends, data pipelines). See `docs/api_setup.md` for the full endpoint reference.

`Api::TokenAuthenticatable` (`app/controllers/concerns/api/token_authenticatable.rb`) is the single bearer-token auth implementation, shared by `Mcp::SessionsController` and `Api::V1::BaseController` — it extracts the token, looks it up via `ApiToken.find_by_raw_token`, sets `Current.user`, and calls `render_unauthorized(message)` on failure; each including controller overrides `render_unauthorized` for its own error envelope shape (JSON-RPC for MCP, `{ error: }` for REST). `Api::V1::BaseController < ActionController::API` also rate limits at 60 req/min (matching MCP — `rate_limit` is declared **before** including `Api::TokenAuthenticatable` in both controllers so unauthenticated requests are throttled too; keep that order), maps `ActiveRecord::RecordNotFound`/`RecordInvalid`/`ActionController::ParameterMissing` to `404`/`422`/`400` JSON errors, and provides a `paginate(scope)` helper (`page`/`per_page`, max 50) that sets `X-Total-Count` and a GitHub-style `Link` header.

Resource controllers (`Api::V1::PostsController`, `CategoriesController`, `TagsController`, `SiteController`, `AssetsController`) and the MCP tools are thin: params in, envelope out. Everything between lives in shared services in `app/services/mcp/`, so the two interfaces return the same data for the same request: `Mcp::PostListQuery` (status/category/tag/search filters plus pagination, returning a `Result(posts, total, page, per_page)`; `page < 1` → 1, `per_page` default 20, max 50), `Mcp::PostWriter.create(user:, attrs:)` / `.update(post:, attrs:)`, `Mcp::SiteInfo.call`, `Mcp::CategorySerializer` / `Mcp::TagSerializer` (`.all(detailed:)`; `detailed: false` is the summary shape inside site info), `Mcp::AssetUploader.call(io:, filename:, content_type:)`, and `Mcp::PostSerializer` (whose `content_plain` is `body_plain`). REST adds pagination headers from the query result; MCP puts `total`/`page`/`per_page` in the body and adds a `markdown` snippet to uploads. There is no REST-specific serializer.

Shared semantics (documented in `docs/api_setup.md` and `docs/mcp_setup.md`): an unknown `category`/`tag` **filter** matches no posts; an unknown `category` on create/update raises `Mcp::PostWriter::UnknownCategory` (REST `422`, MCP failure envelope) and saves nothing; only keys present in `attrs` are written, so passing `category`/`content` blank clears it. `PostWriter` assigns everything and saves **once** inside a transaction (tags are written after the save, in the same transaction), so a published post's edit fires each callback, `post.updated` webhook and fediverse Update once — don't split it back into several `update!` calls. Create always forces `status: :draft`.

### Webhooks (Outbound)
`Webhook` (url, `events` json array, `signing_secret` encrypted, `active`, `consecutive_failures`, `last_triggered_at`, `last_response_code`) lets third-party services subscribe to site events. `Webhook::EVENTS` is the fixed list: `post.published`/`updated`/`deleted`/`scheduled`/`unpublished`, `subscriber.created`/`deleted`, `comment.created`/`approved`. `WebhookDispatcher.deliver(event) { payload }` finds active webhooks subscribed to `event` (`Webhook.subscribed_to`, a `json_each` query) and enqueues `DeliverWebhookJob` per webhook; the payload block runs once, and only when at least one webhook is subscribed; `Webhooks::Sender.post` builds the signed POST and sends it through `Outbound::Connection` (see "Outbound HTTP" below), reading at most `Sender::MAX_RESPONSE_BYTES` (64 KB) of the receiver's body — only the status code is used, so the rest is dropped — and raising `Webhooks::Sender::DeliveryError` on a non-2xx response (redirects included) or network failure. Requests carry `X-Prose-Timestamp` (unix seconds), `X-Prose-Event`, `X-Prose-Delivery` (the job id, stable across retries), and `X-Prose-Signature: sha256=<hex>` where the hex is `HMAC-SHA256(signing_secret, "#{timestamp}.#{raw_body}")` — receivers should compare in constant time and reject stale timestamps. **SSRF protection**: `Webhook` validation uses `Outbound::UrlGuard.blocked_host?` to reject `localhost`/`*.local`/`*.internal` hosts and literal loopback/private/link-local/reserved IPs (incl. IPv4-mapped IPv6), and every send re-checks DNS through `Outbound::Connection`. The job's `retry_on` (polynomial backoff, `DeliverWebhookJob::MAX_ATTEMPTS` = 3) retries failed deliveries and swallows the error once exhausted; every attempt is logged as a `WebhookDelivery` row (pruned inline to the newest `Webhook::DELIVERY_LOG_LIMIT` = 100 per webhook via `Webhook#prune_deliveries!`) and rolls into `Webhook#record_delivery_result!` (log row, prune and result share one transaction; the failure count is incremented in SQL), which resets `consecutive_failures` on success, but only increments it on the **final** failed attempt (`count_failure:`), so one event exhausting its retries counts once; the webhook auto-disables (`active: false`) once `consecutive_failures` reaches `Webhook::MAX_CONSECUTIVE_FAILURES` (5).

Event triggers live at the **model** layer (not controllers), so both the Admin UI and MCP tools fire the same events: `Post::Webhookable` (`after_commit on: [:create, :update]`/`after_destroy_commit`) maps a `status` transition to events: becoming published → `post.published` (including a post created already published), leaving published → `post.unpublished`, becoming scheduled → `post.scheduled` (so published → scheduled sends `post.unpublished` then `post.scheduled`); a never-published scheduled post reverted to draft fires nothing. It also fires `post.updated` and `post.deleted` (destroy) **only for published posts** so draft titles/slugs never leave the site. Status events and `post.deleted` are immediate; `post.updated` is **delayed and coalesced** (see Post Revisions below), so receivers get one event per burst of edits, about two minutes after the last one, carrying the final state. `Subscriber.subscribe_or_sign_in!` fires `subscriber.created` only for a genuinely new subscriber (not a returning magic-link sign-in); `Subscriber#unsubscribe!` fires `subscriber.deleted` (there is no hard subscriber delete in the app, so "deleted" is modeled as unsubscribing). `Comment` fires `comment.created` on `after_create_commit` and exposes `#approve!` (used by `Admin::CommentsController#update` instead of a bare `update!(approved: true)`) which fires `comment.approved`. Per-resource payload serializers live in `app/services/webhooks/` (`PostSerializer`, `SubscriberSerializer`, `CommentSerializer`) — plain hashes with iso8601 timestamps, separate from the MCP serializers since webhook payload shape needs differ.

**Admin UI** (admin role only — both controllers `before_action :require_admin`, and the sidebar link is hidden from writers, since webhooks can exfiltrate subscriber emails): `Admin::WebhooksController` (full CRUD at `/admin/webhooks`) shows the signing secret once via flash on creation or regeneration (`POST .../regenerate_secret`), and a "Send Test Event" button (`POST .../test`) enqueues a `ping` event bypassing subscription filtering. `Admin::WebhookDeliveriesController` (`/admin/webhooks/:webhook_id/webhook_deliveries`) shows the delivery log (event, response code, timestamp, success/fail) for one webhook.

### Outbound HTTP (SSRF Guard)
`Outbound::Connection.request(uri, net_http_request, max_bytes:, truncate: false)` (`app/services/outbound/connection.rb`) is the one guarded connection for attacker-controlled URLs, shared by `Webhooks::Sender` and `ActivityPub::HttpClient`; those classes only build the request and map statuses/errors. It calls `Outbound::UrlGuard.resolve!` (every DNS answer must be public, else `UrlGuard::UnsafeUrlError` before anything is sent) and pins the socket to that vetted IP with `Net::HTTP#ipaddr=`, so a DNS rebind between check and connect can't reach an internal address. It never follows redirects (a 3xx comes back as a status), sets 5s open / 10s read / 10s write timeouts, and streams the body: past `max_bytes` it raises `Outbound::Connection::ResponseTooLarge`, or with `truncate: true` stops reading, closes the connection and returns the first `max_bytes`. It returns `Response(code, body, truncated)` and lets network errors propagate. `Outbound::UrlGuard` (`blocked_host?`, `blocked_ip?`, `resolve!`) is also what `Webhook` URL validation uses; its error messages are deliberately feature-neutral. Don't open a `Net::HTTP` to a user- or remote-supplied URL anywhere else. `test/services/outbound/connection_test.rb` proves pinning, no-redirect and the cap against a real loopback socket (the host is `pinned.invalid`, which can't resolve, so reaching the server proves the pin). `OembedFetcher` deliberately doesn't use it: its endpoints are fixed provider hosts, not user input.

### Fediverse (ActivityPub)
Opt-in via `SiteSetting#activitypub_enabled` (Admin → Settings → Fediverse); while off, every ActivityPub route 404s (`ActivityPub::BaseController#require_federation`) and post URLs serve only HTML. The whole site is **one actor** (`@<activitypub_username>@APP_HOST`, a `Person` at `/activitypub/actor`) — there are no per-author actors. Enabling federation the first time generates an RSA-2048 keypair on `SiteSetting` (`activitypub_private_key` is encrypted); it is never rotated automatically because remote servers cache it by key id. Because the actor id is the URL `/activitypub/actor` (not the username), changing the username doesn't break existing follows, but changing `APP_HOST` does.

Everything lives under the `ActivityPub::` namespace (`app/controllers/activity_pub/`, `app/services/activity_pub/` — the directory is `activity_pub` so Rails' default inflection yields `ActivityPub`). **`ActivityPub::Urls` is the single source of every ActivityPub id**: it builds absolute URLs from `AppUrlOptions` (APP_HOST in production), never from the request host, so a URL served by a controller matches the one a background job delivers. It also has `post_for(uri)`, which maps an incoming object id back to a live `Post` (only this host, only `/posts/:slug`). Note `post_url(slug: post.slug, ...)` — passing the record positionally *and* `slug:` puts the record in the `:format` slot (see "Slug Route Helpers" below).

Endpoints: `/.well-known/webfinger`, `/activitypub/actor`, `/activitypub/inbox` (also advertised as the shared inbox), `/activitypub/outbox` (20 newest live posts), `/activitypub/followers` and `/following` (counts only — follower identities are never published). `GET /posts/:slug` with an `application/activity+json` or `ld+json` Accept header is routed to `ActivityPub::ObjectsController` by a lambda route constraint (`ActivityPub::Negotiation`) placed before `resources :posts`, so `PostsController` stays HTML-only; `posts/show` adds a `<link rel="alternate" type="application/activity+json">`.

**Signatures**: `ActivityPub::Signature` implements draft-cavage HTTP Signatures (RSA-SHA256 over `(request-target) host date [digest]`, with a SHA-256 `Digest` of the body); the verifier requires those headers to be signed, a Date within 12h (1h future skew), and a matching digest. `ActivityPub::RequestVerifier` resolves the signer via `ActivityPub::ActorFetcher.for_key_id` (cached as a `FediverseActor`, refetched after a day or once on verification failure to pick up key rotation), and the inbox rejects any activity whose `actor` isn't the signer. `ActorFetcher` only accepts a document whose `id` equals the URI requested and whose `publicKey.owner` is that actor. **All outbound HTTP (actor fetches and deliveries) goes through `ActivityPub::HttpClient`**, which sends through `Outbound::Connection` (SSRF guard, IP pinning, no redirects, timeouts — see "Outbound HTTP" below) with bodies capped at `MAX_RESPONSE_BYTES` (1 MB, raising on overflow), signs GETs too (for "authorized fetch" servers), and refuses plain http in production.

**Inbox** (`ActivityPub::InboxProcessor`): `Follow` of our actor → `FediverseActor#follow!` + an `Accept` delivered via `DeliverActivityJob`; `Undo` of a Follow/Like; `Like` of a live post → `FediverseLike` (unique per actor/post; count shown on the admin post dashboard); `Create(Note)` that is public, attributed to the signer, hosted on the signer's domain, and `inReplyTo` a live post (or a top-level fediverse comment) → a `Comment` with `approved: false` and `activitypub_uri` (unique, so redelivery is a no-op), authored by an `Identity` created lazily via `FediverseActor#ensure_identity!` (no handle). Note HTML is converted to plain text by `ActivityPub::CommentBody` — remote HTML is never stored — and a leading mention of our actor is stripped. `Delete` soft-deletes the signer's own comment, or, when the object is the actor itself, removes its follow and likes. An unverifiable `Delete` of an actor by itself (the account is gone, so its key 410s) is acknowledged with 202 and ignored. Replies to replies are dropped (comments are one level deep), and `Update(Note)` is not handled.

**Outbound** (`Post::Federatable`, mirroring `Post::Webhookable`): transition to `published` (including create-as-published) → `FederatePostJob("create")`; transition away from published or destroy → `"delete"` (a Tombstone; the URL is passed in since the post may be gone); a new revision of a published post → `"update"`, **delayed and coalesced** the same way as the `post.updated` webhook (see Post Revisions below). `FederatePostJob` builds the activity (`ActivityPub::Activities` + `ActivityPub::ArticleSerializer`) and enqueues one `DeliverActivityJob` per `FediverseActor.follower_inboxes` (shared inboxes deduplicated). Articles carry full HTML only for `visibility_public?` posts — members-only/paid posts send `seo_description` + a "Read more" link — and rich-text attachments are flattened to plain `<img>`/`<a>` tags with absolute URLs by `RichTextFlattener`. `DeliverActivityJob` retries (polynomial, 5 attempts) on 5xx/429/network errors, drops 4xx, and on `410 Gone` unfollows every follower behind that inbox.

Tests share `ActivityPubTestHelper` (`test/support/activity_pub_helper.rb`, included per test class): `enable_federation!`, `remote_actor`, `remote_key` (generated lazily, once per worker) and `signed_inbox_headers(body)` (signs as that remote actor).

### Absolute URLs
`AppUrlOptions.call` (`app/services/app_url_options.rb`) is the single source of host/port/protocol for URLs built outside a request (webhook payloads, the email logo, and ActivityPub ids via `ActivityPub::Urls.url_options`). It reads `config.action_mailer.default_url_options` and, when that has no protocol, uses `https` if `force_ssl` is on. `production.rb` also sets `protocol:` there so mailer links match. Don't read `default_url_options` anywhere else.

### Slug Route Helpers
`posts`, `categories`, and `tags` are routed with `param: :slug`, so call their helpers with the keyword only: `post_path(slug: post.slug)`, `category_url(slug: category.slug)`, `tag_url(slug: tag.slug)`; authors are routed with `param: :handle`, so `author_path(handle: identity.handle)`. Passing just the record (`post_path(post)`) works for posts because `Post#to_param` returns the slug; `Identity` defines no `to_param`, so authors always take `handle:` alone. **Never pass both** (`post_url(post, slug: post.slug)`): the explicit `slug:` fills `:slug`, so the positional record falls through to the optional `:format` segment and yields `/posts/my-post.my-post`. Nested routes (`post_love_path`, `post_comments_path`) use `:post_slug`, so pass the record positionally there. Tests should assert against literal paths (`"/posts/#{post.slug}"`) rather than a route helper, or they can reproduce the very bug they check for.

### Content Export
Admins export the site from `/admin/exports` (`Admin::ExportsController`, admin role only; linked from the sidebar and `/admin/settings`). `Export` (`format` enum `markdown`/`json` with `validate: true`, so an unknown format is a validation error rather than an `ArgumentError`; `status` enum `pending`/`processing`/`completed`/`failed`; `has_one_attached :file`) keeps only the newest `Export::RETENTION_LIMIT` (10) rows, pruned `after_create_commit`. `ExportJob` calls `Export#exporter` (`Export.exporter_for(format)` → `Exports::MarkdownExporter` / `Exports::JsonExporter`, both in `app/services/exports/`, each `.call` returning a rewound `Tempfile` the caller must `close!`), attaches the result, and `broadcast_replace_to "exports"` with the `admin/exports/_export` partial so the index row updates live. Any exporter error marks the export `failed` with `error_message` instead of raising.

`Exports::MarkdownExporter` writes `posts/<slug>.md`, `pages/<slug>.md` (YAML front matter + body converted with the `reverse_markdown` gem) and `images/<blob id>-<slugified filename>` into a zip via `rubyzip` (streamed with `Zip::OutputStream`; blobs are downloaded in chunks). Rich text attachments are rewritten *before* HTML→Markdown conversion by `RichTextFlattener` (`app/services/rich_text_flattener.rb`, shared with `ActivityPub::ArticleSerializer`): image blobs become `<img>` tags, other blobs become links, and `XPost`/`YouTubeVideo` embeds become plain URL links. Each caller passes only a blob-URL block (`../images/...` here, absolute URLs for ActivityPub) and `wrap:` (a paragraph per attachment here). Add a new embed type there. Filenames are slugified because a space in a Markdown link target breaks the link.

`Exports::JsonExporter` emits `{ format: "prose", version:, site:, authors:, categories:, tags:, posts:, pages:, navigation_items:, subscriber_labels:, subscribers: }` with rich text as HTML (`content_html`). **Site settings use the explicit `SITE_SETTING_ATTRIBUTES` allowlist**, not a denylist, so a newly added API key column is never exported by accident — add a column there only if it's safe to hand out. Password digests and subscriber auth tokens are never included. `.call` streams the document into the tempfile so memory doesn't grow with table size: collections are lazy Enumerators (`each_in_batches` for the id-ordered ones, `in_order` for the small ones with their own sort order) written one record at a time, and the bytes are identical to `JSON.pretty_generate(as_json)`, which a test asserts. Add a new top-level key in `#document`.

Downloads go through `Admin::ExportDownloadsController` (`GET /admin/exports/:id/download`), which uses `ActiveStorage::Streaming#send_blob_stream` behind `require_admin` rather than redirecting to an Active Storage blob URL — those signed URLs don't expire, and a JSON export contains every subscriber email. It's a separate controller because `ActiveStorage::Streaming` includes `ActionController::Live`. `rubyzip` must stay a direct `Gemfile` dependency: it's otherwise only pulled in transitively by `selenium-webdriver` in the test group.

### Authentication
- **Admin**: session-based (signed cookie, 14-day expiry). The `Authentication` concern owns cookie → `Session` resumption (`resume_session`, memoized via a `Current.session` short-circuit) and is included once on `ApplicationController`, so both admin (`current_user`) and identity (`IdentityAuthentication#current_identity`) lookups share a single `sessions` query per request.
- **Admin Passkeys**: optional WebAuthn/passkey sign-in alongside password. Configured via `WEBAUTHN_ORIGIN` and `WEBAUTHN_RP_ID` env vars. Managed at `/admin/passkeys`.
- **Subscribers**: passwordless magic-link (15-minute token expiry)
- **MCP/API**: Bearer token (`prose_`-prefixed, SHA256 digest stored)

## Git Workflow

This project follows **GitHub Flow** (Feature Branch Workflow). All development happens on feature branches created from `master`. The `master` branch is always deployable.

### Rules

1. **Never commit directly to `master`.** Always create a feature branch.
2. **Branch from `master`** for every change — features, bug fixes, docs, refactors.
3. **Name branches descriptively**: `fix-typography-preview`, `add-subscriber-export`, `update-tailwind-config`.
4. **Before opening a pull request**, ensure:
   - All unit tests pass: `bin/rails test`
   - Linting passes with no offenses: `bin/rubocop`
   - Security scans are clean: `bin/brakeman --quiet --no-pager --exit-on-warn --exit-on-error`
5. **Submit a pull request** to merge back into `master`. PRs require review before merging.
6. **Keep PRs focused.** One logical change per PR — don't bundle unrelated work.

### Typical Workflow

```bash
git checkout master && git pull
git checkout -b my-feature-branch
# ... make changes ...
bin/rails test && bin/rubocop        # Verify before committing
git add <files> && git commit
git push -u origin my-feature-branch
gh pr create                          # Open pull request against master
```

## Code Style

- **Linter**: RuboCop with `rubocop-rails-omakase` preset (`.rubocop.yml`)
- **Testing**: Minitest with parallel execution; fixtures loaded from `test/fixtures/*.yml`. Shared helpers live in `test/support/` and are required by `test_helper.rb`: `StubbingHelper` (`with_singleton_stub`, `with_instance_stub`, `with_const`; Minitest 6 dropped `Object#stub`, and these restore exactly what they found, so never stub with a bare `define_method`/`remove_method`), `HttpHelper` (`FakeHTTP`, `with_fake_http`, `stub_oembed_fetch`, `stub_client_chat`), `BulkEnqueueHelper` (include per test class; see Background Jobs), `StripeHelper` (`configure_stripe!`/`unconfigure_stripe!`; the test transaction rolls settings back, so no teardown is needed) and, for integration tests, `ApiHelper` (`ADMIN_API_TOKEN`/`WRITER_API_TOKEN`/`REVOKED_API_TOKEN`, `api_auth_header`, `mcp_headers`, `mcp_call`, `parse_tool_result`). User fixtures hash passwords at `BCrypt::Engine::MIN_COST` to keep sign-ins cheap.
- Composition over inheritance; explicit dependencies over implicit magic

## Deployment

Docker + Kamal. SQLite databases persisted via volume mount (`prose_storage:/rails/storage`). Solid Queue runs in-process with Puma (`SOLID_QUEUE_IN_PUMA=true`). See the README for the full deployment guide.

**No credentials file** — the project does not use `config/credentials.yml.enc` or `config/master.key`. Instead:
- **Development/Test**: hardcoded Active Record Encryption keys in `config/environments/development.rb` and `test.rb`
- **Production**: all secrets come from ENV variables (`SECRET_KEY_BASE`, `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`, etc.)
- **Secret generation**: `bin/rails prose:generate_secrets` produces all required production secrets
- **Kamal secrets**: stored in `.kamal/.env` (gitignored), sourced by `.kamal/secrets`
