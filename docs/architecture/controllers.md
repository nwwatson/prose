# Controllers & Admin UI

Shared controller concerns, admin settings, index pagination and the admin view partials and helpers.

## Controller Pattern
Skinny controllers that delegate to models/services. Controllers handle only HTTP concerns.

`Admin::EditorResource` (`app/controllers/concerns/admin/editor_resource.rb`) is a shared concern for the three editor-backed admin controllers (`Admin::PostsController`, `Admin::PagesController`, `Admin::NewslettersController`). It sets `layout :choose_layout` (editor layout on `new`/`edit`/`create`/`update`, `"admin"` elsewhere — declared per-controller via `uses_editor_layout "admin_editor"` etc.) and provides `respond_with_saved(record, notice:, status:)` / `respond_with_errors(record, template)` for the shared HTML+JSON `respond_to` branches on `create`/`update`. Including controllers implement `resource_json(record)` and `edit_path_for(record)` to supply their resource-specific JSON payload and redirect target; anything else that differs (e.g. `Post#create_version_if_needed!` after update) stays in the controller.

`Admin::CrudResource` (`app/controllers/concerns/admin/crud_resource.rb`) supplies `new`/`create`/`edit`/`update`/`destroy` for the plain admin resources (categories, mailing lists, subscriber labels, membership tiers, segments, webhooks). A controller includes it, calls `crud_resource Model` (options: `as:` for the view ivar name, e.g. `@tier`/`@label`; `flash_scope:`, default `flash.admin.<plural>`; `member_actions:` for extra actions that need the record loaded) and defines private `resource_params`. It redirects to the resource's index (`after_save_path`). The exceptions are overrides: categories' `find_resource` looks up by slug, tiers override `new` (default currency) and `destroy` (refused while it has members), webhooks override `new`, `create` (`super { flash[:raw_secret] = ... }`) and `after_save_path` (a new webhook goes to its edit page). A webhooks-style `before_action` that must run before the record loads is declared above `crud_resource`.

The editor's two oEmbed attachment controllers (`Admin::XPostsController`, `Admin::YouTubeVideosController`) share `create` through `Admin::OembedEmbeddable`; each defines only `embed_class` and `embed_error_message` (the fallback when there are no validation errors to report).

Index status filters go through `Admin::BaseController#filter_by_status(scope, allowed, value: params[:status])`, which applies the named model scope only for whitelisted values (a Hash maps a param value to a differently named scope, as comments' `pending` does). Never pass a status param straight to `where`. API token visibility (admins see all, writers their own) is `ApiToken.visible_to(user)`.

## Admin Settings & Masked Secrets
`Admin::SettingsController` and `Admin::NewsletterSettingsController` share their `edit`/`update` actions via the `Admin::SiteSettingsResource` concern (`app/controllers/concerns/admin/site_settings_resource.rb`); each controller only defines `site_setting_params`, `redirect_path`, and `notice_key`. The `SiteSetting::MaskedSecrets` concern (`app/models/site_setting/masked_secrets.rb`) owns the "••••••••" placeholder mask for encrypted keys (`SECRET_ATTRIBUTES`): `assign_attributes_ignoring_mask(attrs)` drops any secret attribute whose submitted value is still the mask (leaving the stored key unchanged), while a blank value still clears it; `masked_value_for(attribute)` is what views call to render the mask (or "") for a password field's current value.

## Admin Index Pagination
`Admin::BaseController` includes the public site's `Paginatable` concern with `PER_PAGE = 50` as the default, so admin actions call `paginate(scope)` (sets `@page` / `@next_page`). Subscribers, posts, comments, memberships, newsletters, segments, the segment show page's matching subscribers and a newsletter's delivery log are paginated. Give a paginated scope a unique tie-breaker (`id`) in its order so rows can't repeat or vanish between pages. Views render `admin/shared/_pagination` (`page:`, `next_page:`), which keeps every other query param (filters, search) on its links; render it outside the empty-state conditional so a page past the end still links back. A total shown beside a paginated list must come from the unpaginated source (e.g. `Segment#subscriber_count`), never from the page's relation.

Index views render their mobile cards and desktop table rows from `_card` / `_row` partials with `collection:`, and test for emptiness with `@records.load.any?` (not `any?`, which runs an extra `EXISTS`).

Subscriber filtering lives in `Subscriber.search(term)` (email or handle) and `Subscriber.with_label(id)`; blank arguments don't filter. `with_label` is a subquery, not a join, so preloaded labels aren't narrowed to the filtered one.

## Admin Shared Partials
Common admin view markup is factored into partials under `app/views/admin/shared/`: `_page_header` (`title:`, `action:` — an optional safe-HTML block for the header's trailing button/links; `stack: false` keeps the action beside the title on mobile, as the edit pages' Delete button does), `_empty_state` (`description:`, optional `title:`/`action_label:`/`action_path:`) for the "no records yet" dashed-border box, `_reveal_secret` (`secret:`, `message:`, `copy_label:`, optional `wrapper_class:`) for the green box showing a token or signing secret once; its copy button is the admin `clipboard` controller, which reads the secret from the DOM, so never interpolate one into JavaScript (no inline `onclick` in views), `_form_errors` (`record:`, optional `heading:` and `wrapper_class:`) for the red error-summary box above a form, and `_stat_card` (`label:`, `value:`, optional `trend:`/`note:`, `wrapper_class:` for grid classes such as `col-span-*`, `value_class:` e.g. `capitalize`) for the white bordered metric tiles on dashboard/analytics pages — `_stat_card_bordered` covers the differently-styled tiles on the revenue page. Analytics pages (dashboard, traffic, growth, post dashboard) build their cards from three more: `_panel` (`title:`, optional `action:` for trailing header content such as a "View details" link or range selector, `stack: true` to put it under the title on mobile as the chart panels do, `wrapper_class:`, `data:` for a chart controller mounted on the card; the block is the body), `_count_table` (`headers:`, `rows:` — cell arrays, or a label => count Hash; the first column is the label and the rest are right-aligned; `empty:`) and `_bar_list` (`counts:` Hash, `empty:`, optional `limit:`; bars are relative to the largest count). The two list partials render their own empty text, so a view never wraps them in `any?`. Don't hand-write a stat card or panel to add a class: use `wrapper_class:`. `AdminHelper` adds matching helper methods: `status_badge(label, color_class:, size: :md/:sm)` renders the pill used for post/page/newsletter/membership/subscriber/token statuses (with per-model `*_status_color` helpers supplying the color classes — use them on both index and show pages, never an inline `case`), `subscriber_label_pill(label)` renders a subscriber label in its own colour, `admin_tab_link(label, path, active:)` is an underlined filter tab, and `admin_button_classes(variant: :primary/:outline/:danger, size: :sm/:md/:lg, extra:)`, `admin_input_classes(shape: :block/:inline/:suffix, extra:)`, `admin_th_classes` return the shared Tailwind class strings for buttons, form inputs, and table header cells so views interpolate them instead of repeating the literal class lists. Change padding or layout through `size:`/`shape:`, not a conflicting utility in `extra:`.

Form markup goes through four more partials plus `admin_label_classes(extra:)` and `admin_hint_classes`; use the helpers wherever the markup doesn't fit a partial, never the literal label or hint classes:
- `_field` (`form:`, `attribute:`, optional `label:`, `hint:`, `wrapper_class:`) — label, input (the block) and hints. A nil `label:` uses the attribute's translation, `hint:` takes a string or an array, `wrapper_class:` defaults to `"mt-2"` and is `nil` for `custom_select`/`tag_select`, which bring their own wrapper. `data-*`, `form=` and ids stay on the inputs in the block.
- `_color_field` (`form:`, `attribute:`, `label:`, `target:`, `compact:`) — the `color-pair` swatch and hex input; `target:` is the preview controller's data hash (e.g. `{ dark_theme_preview_target: "bgColor" }`), `compact: true` is the newsletter-settings size.
- `_secret_field` (`form:`, `attribute:`, `label:`, `placeholder:`, `hint:`) — every `SiteSetting::MaskedSecrets` key. It renders `masked_value_for`, so don't hand-write a `password_field` for a stored key; add the attribute to `SECRET_ATTRIBUTES` too.
- `_settings_section` (`title:`, `description:`, optional `data:`, `divider:`) — fieldset and legend header; the block is the body with its own spacing wrapper. Controller attributes go in `data:`.

The three typography groups on the settings page are one loop in `admin/settings/_typography`.
