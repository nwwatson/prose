# Subscribers & Email

Subscriber segmentation, email/payment provider adapters, mailer branding, digests and mailing lists.

## Subscriber Segmentation
`SubscriberLabel` provides tagging for subscribers (name + hex color). `SubscriberLabeling` is the many-to-many join. `Segment` stores saved filter criteria as JSON (`filter_criteria` column) with a `Segment::Resolvable` concern that delegates to `SegmentSubscribersQuery`. Filters support: label matching (any_of/all_of/none_of), date ranges on `confirmed_at`, and engagement level (active/inactive derived from `newsletter_deliveries`). Newsletters have an optional `mailing_list_id` and `segment_id` — `Newsletter::Sendable#target_subscribers` starts from the list's `recipients` (or all confirmed subscribers) and, when a segment is set, narrows that audience with `segment.resolve(audience)` (`SegmentSubscribersQuery.new(criteria, scope:)` filters the given scope instead of always starting from `Subscriber.confirmed`). Admin CRUD at `/admin/subscriber_labels`, `/admin/segments`. Labels are managed per-subscriber at `/admin/subscribers/:id`. A segment's `subscriber_count` is a multi-subquery COUNT, so don't call it per option: the newsletter editor lists names only, and its `segment_count` Stimulus controller fetches the selected segment's count from `segments#count` (URL in each option's `data-count-url`).

`Segment::CriteriaBuilder` owns the flat-form ↔ `filter_criteria` JSON translation so `Admin::SegmentsController` only permits params. It declares virtual `attribute`s (`label_ids`, `label_mode`, `subscribed_after`, `subscribed_before`, `engagement`) and a `before_validation :build_filter_criteria` that merges them into the `filter_criteria` hash (`label_ids.reject(&:blank?).map(&:to_i)`, `label_mode.presence || "any_of"`). Only attributes assigned since the last save (`*_came_from_user?`) replace their stored criterion, and a blank value removes it, so `update!(name:)` leaves the criteria alone; the form therefore sends a hidden blank `segment[label_ids][]` so unchecking every label clears them. The public readers fall back to the stored `filter_criteria` hash when the virtual attribute itself is unset, so `segments/_form` can read `segment.label_ids` / `segment.label_mode` / etc. directly instead of parsing `filter_criteria` — this is what makes the edit form round-trip from the stored JSON.

## Email & Payment Provider Adapters
`EmailService` and `PaymentService` each follow the same provider pattern: a module-level `.provider` factory builds the configured adapter from `SiteSetting` (injecting keys/secrets into the constructor rather than having the adapter read `SiteSetting` itself), and `.configured?` reports whether the feature is usable. Both adapter interfaces are declared on a `Base` class (`EmailService::Base`, `PaymentService::Base`) that the concrete adapters subclass. `EmailService::Base#deliver_newsletter(newsletter, subscriber)` is the single entry point callers use — `SendNewsletterJob` always calls `provider.deliver_newsletter`, with no provider branching in the job. `deliver_newsletter` is synchronous and must raise when the provider did not accept the message: `EmailService::Smtp#deliver_newsletter` delivers `NewsletterMailer#campaign` with `deliver_now` (forcing `raise_delivery_errors` on that message), and `EmailService::Sendgrid#deliver_newsletter` renders that same mailer and posts it via the SendGrid API (`#send_email`, one memoized API client per adapter instance), raising `EmailService::DeliveryError` on a non-2xx response.

`SendNewsletterJob` delivers at-least-once. It walks the subscribers with no `NewsletterDelivery` row and writes that row (one `insert` per recipient, `unique_by` the newsletter/subscriber index) only **after** `deliver_newsletter` returns, so a row means "the provider accepted it". A provider error for one subscriber is logged and the loop continues (a run stops early after `MAX_CONSECUTIVE_FAILURES` rejections in a row); if anyone failed the job raises `PartialDeliveryError`, and `retry_on` (`MAX_ATTEMPTS` = 5, polynomial backoff) reruns it from the still-undelivered subscribers, so nobody delivered is sent to again. The one duplicate window is a crash between the provider accepting and the row being written. When retries run out the newsletter is still marked sent. `Newsletter#mark_sent!` defaults `recipients_count` to the deliveries recorded across every run. The job returns at once unless the newsletter is `sending`, and `limits_concurrency` keeps two runs for one newsletter from overlapping. SendGrid webhook event processing (updating `NewsletterDelivery` open/click/bounce/unsubscribe state) lives in `EmailService::Sendgrid::WebhookProcessor`, used directly by `Webhooks::SendgridController` — it needs no API key, since it never calls the SendGrid API. Open/click events are written with SQL (`update_all`), never read-modify-write, so concurrent events don't lose increments. `PaymentService::Stripe` is constructed with `secret_key:`, `publishable_key:`, and `webhook_secret:` all injected by `PaymentService.provider` from `SiteSetting`, so `construct_webhook_event` never reads `SiteSetting` directly. `EmailService.from_address` is the single `SMTP_FROM` env lookup, used by both `ApplicationMailer`'s default `from` and `EmailService::Sendgrid`.

## Mailer Branding & Layout
`SiteSetting::EmailBranding#email_branding` resolves the seven branding fields (accent/background/body/heading colors with `DEFAULT_*` constant fallbacks, font stack, footer text, site name, logo URL) into one hash. `ApplicationMailer#load_email_branding` sets `@email_settings` from it (plus per-field ivars the individual mailer templates read); `Newsletter::Templatable#email_settings` merges the same hash with newsletter-specific overrides (resolved template/accent color/preheader text, social links) rather than re-deriving the color fallbacks. `ApplicationMailer#prepare_subscriber_links(subscriber)` sets `@unsubscribe_url`, `@email_preferences_url` and the `List-Unsubscribe`/`List-Unsubscribe-Post` headers for `NewsletterMailer#campaign`, `PostNotificationMailer#new_post` and `DigestMailer#digest`.

**Emailed link tokens live on the models** (`Subscriber#unsubscribe_token` / `.find_by_unsubscribe_token`, `Subscriber#email_preferences_token`, `Comment#notification_token`): controllers and mailers never call `message_verifier` themselves. The verifier names (`"unsubscribe"`, `"email_preferences"`, `"comment_notification"`) and 30-day expiry must not change, or links already in inboxes break. `app/views/mailer/_cta_button.html.erb` (`url:, label:, color:`) is the shared CTA table used by `post_notification_mailer/new_post`, `subscriber_mailer/confirmation`, `subscriber_mailer/magic_link`, and `comment_mailer/reply_notification`. `app/views/mailer/_footer.html.erb` (`settings:`, reads `@unsubscribe_url` directly) is shared by the three newsletter templates (`newsletter_mailer/_template_*`) and by `layouts/mailer.html.erb` (used by `post_notification_mailer`, `subscriber_mailer`, `comment_mailer`) — the layout keeps its own header markup since it supports a logo fallback the newsletter's minimal template doesn't.

## Email Frequency & Digests
`Subscriber::EmailPreferences` adds `email_frequency` (enum `immediate`/`weekly`/`monthly`/`none`, `prefix: :email`, `validate: true`, default `immediate`). The frequency governs **post emails only**: `SendPostNotificationsJob` sends to `post.notification_recipients.email_immediate`, and `SendDigestsJob` covers `weekly`/`monthly`. Newsletters ignore it (`Newsletter::Sendable#target_subscribers` is unchanged), so `none` means "no post emails", not unsubscribed.

`SendDigestsJob.perform(frequency)` runs from `config/recurring.yml` (`"0 8 * * 1"` weekly, `"0 8 1 * *"` monthly, server time zone). `subscribers.last_digest_at` is a **delivery cursor**, meaning "posts published before this have reached the subscriber", not strictly "when a digest was last sent". `#digest_window_start(now)` is `last_digest_at || now - period`. The job lists `Post.live.where(published_at: since...now)` (half-open, so consecutive windows neither overlap nor gap) limited to posts on the subscriber's active mailing lists (subscribers on no active list are skipped and keep their cursor), caches the lookup per distinct (window start, list ids) pair, builds a `DigestMailer.digest(subscriber, post_ids.first(POST_LIMIT), total_count)`, then, per batch, bulk-enqueues those digests and `update_all`s `last_digest_at` to the run's `now`. A retried run therefore finds empty windows, and a subscriber with no new posts keeps their cursor. A `before_save` moves the cursor when the frequency changes: from `immediate` it jumps to now (those posts were already emailed individually), from `none` it clears (falls back to the last period), and between `weekly` and `monthly` it is kept. `DigestMailer` reloads `Post.live` at delivery time and returns without mailing if the subscriber has since unsubscribed or every post was unpublished. It shows `seo_description` as the excerpt (already public in meta tags, so it doesn't leak gated content beyond what the page head does), and uses a non-WebP featured-image variant because email clients can't render WebP.

Subscribers manage the setting at `/email-preferences` (`EmailPreferencesController`; `email-preferences` is a reserved `Page` slug). Access is either a signed `token` param (`Subscriber#email_preferences_token` / `.find_by_email_preferences_token`, message verifier purpose `"email_preferences"`, 30-day expiry, separate from the `"unsubscribe"` token) or a signed-in `current_subscriber`. `ApplicationMailer#prepare_subscriber_links` sets `@email_preferences_url`, which `mailer/_footer` renders beside the unsubscribe link, and the unsubscribe confirmation page links to it as an alternative. In mailer templates build post links with `post_url(slug: post.slug)`: `post_url(post, slug: ...)` puts the record in the `:format` slot and yields `/posts/<slug>.<slug>`.

## Mailing Lists (Multiple Newsletters)
`MailingList` is the subscribable list readers see as a "newsletter" — **not** `Newsletter`, which is a one-off email campaign (the name was taken by #22). Lists have `name`, `slug` (`Sluggable`), `description`, `frequency` (free-text label such as "Weekly", shown to subscribers; it doesn't schedule anything), `active` and `subscribe_by_default`. Inactive lists are hidden from subscribers and the post editor and receive no post emails; subscriptions to them are kept so reactivating restores them. Admin CRUD at `/admin/mailing_lists` (`Admin::MailingListsController`, open to writers like labels/segments), with confirmed-subscriber counts from `MailingList.subscriber_counts`.

Subscribers: `Subscriber::ListSubscribable` joins every `MailingList.subscribed_by_default` list `after_create`. The `/email-preferences` page shows a checkbox per active list (only when more than one is active) that writes `selected_mailing_list_ids`, a virtual attribute synced `after_save` — it only replaces subscriptions to *active* lists. Global unsubscribe (`unsubscribed_at`) is separate and always wins, since recipients are always built from `Subscriber.confirmed`.

Posts: `Post::Notifiable` gives new posts the default lists in `after_initialize` **unless** `mailing_list_ids=`/`mailing_lists=` was called (the editor always submits a hidden `""` plus its checkboxes, so unchecking every list means "email nobody"). The new-post email fires from an `after_commit` on any transition to `published` — not from `publish!` — so the admin editor (which saves `status` directly), the API, MCP and `PublishScheduledPostsJob` all notify. `posts.subscribers_notified_at` is claimed with a conditional `update_all` before `SendPostNotificationsJob` is enqueued, so unpublish/republish never emails twice; code that creates already-published posts without wanting emails (seeds, imports) should set `subscribers_notified_at`. `Post#notification_recipients` is `Subscriber.confirmed.subscribed_to(mailing_lists.active)`. API/MCP don't accept list ids yet, so posts created there use the default lists.

The `CreateMailingLists` migration folds existing installs into one default "Newsletter" list (every non-unsubscribed subscriber, every post) and stamps published posts as notified. The JSON export includes `mailing_lists` and `mailing_list_ids` on posts and subscribers.
