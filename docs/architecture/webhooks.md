# Webhooks & Outbound HTTP

Outbound webhooks and the shared SSRF-guarded connection.

## Webhooks (Outbound)
`Webhook` (url, `events` json array, `signing_secret` encrypted, `active`, `consecutive_failures`, `last_triggered_at`, `last_response_code`) lets third-party services subscribe to site events. `Webhook::EVENTS` is the fixed list: `post.published`/`updated`/`deleted`/`scheduled`/`unpublished`, `subscriber.created`/`deleted`, `comment.created`/`approved`. `WebhookDispatcher.deliver(event) { payload }` finds active webhooks subscribed to `event` (`Webhook.subscribed_to`, a `json_each` query) and enqueues `DeliverWebhookJob` per webhook; the payload block runs once, and only when at least one webhook is subscribed; `Webhooks::Sender.post` builds the signed POST and sends it through `Outbound::Connection` (see [webhooks.md](webhooks.md#outbound-http-ssrf-guard)), reading at most `Sender::MAX_RESPONSE_BYTES` (64 KB) of the receiver's body — only the status code is used, so the rest is dropped — and raising `Webhooks::Sender::DeliveryError` on a non-2xx response (redirects included) or network failure. Requests carry `X-Prose-Timestamp` (unix seconds), `X-Prose-Event`, `X-Prose-Delivery` (the job id, stable across retries), and `X-Prose-Signature: sha256=<hex>` where the hex is `HMAC-SHA256(signing_secret, "#{timestamp}.#{raw_body}")` — receivers should compare in constant time and reject stale timestamps. **SSRF protection**: `Webhook` validation uses `Outbound::UrlGuard.blocked_host?` to reject `localhost`/`*.local`/`*.internal` hosts and literal loopback/private/link-local/reserved IPs (incl. IPv4-mapped IPv6), and every send re-checks DNS through `Outbound::Connection`. The job's `retry_on` (polynomial backoff, `DeliverWebhookJob::MAX_ATTEMPTS` = 3) retries failed deliveries and swallows the error once exhausted; every attempt is logged as a `WebhookDelivery` row (pruned inline to the newest `Webhook::DELIVERY_LOG_LIMIT` = 100 per webhook via `Webhook#prune_deliveries!`) and rolls into `Webhook#record_delivery_result!` (log row, prune and result share one transaction; the failure count is incremented in SQL), which resets `consecutive_failures` on success, but only increments it on the **final** failed attempt (`count_failure:`), so one event exhausting its retries counts once; the webhook auto-disables (`active: false`) once `consecutive_failures` reaches `Webhook::MAX_CONSECUTIVE_FAILURES` (5).

Event triggers live at the **model** layer (not controllers), so both the Admin UI and MCP tools fire the same events: `Post::Webhookable` (`after_commit on: [:create, :update]`/`after_destroy_commit`) maps a `status` transition to events: becoming published → `post.published` (including a post created already published), leaving published → `post.unpublished`, becoming scheduled → `post.scheduled` (so published → scheduled sends `post.unpublished` then `post.scheduled`); a never-published scheduled post reverted to draft fires nothing. It also fires `post.updated` and `post.deleted` (destroy) **only for published posts** so draft titles/slugs never leave the site. Status events and `post.deleted` are immediate; `post.updated` is **delayed and coalesced** (see [posts.md](posts.md#post-revisions-coalesced-updates)), so receivers get one event per burst of edits, about two minutes after the last one, carrying the final state. `Subscriber.subscribe_or_sign_in!` fires `subscriber.created` only for a genuinely new subscriber (not a returning magic-link sign-in); `Subscriber#unsubscribe!` fires `subscriber.deleted` (there is no hard subscriber delete in the app, so "deleted" is modeled as unsubscribing). `Comment` fires `comment.created` on `after_create_commit` and exposes `#approve!` (used by `Admin::CommentsController#update` instead of a bare `update!(approved: true)`) which fires `comment.approved`. Per-resource payload serializers live in `app/services/webhooks/` (`PostSerializer`, `SubscriberSerializer`, `CommentSerializer`) — plain hashes with iso8601 timestamps, separate from the MCP serializers since webhook payload shape needs differ.

**Admin UI** (admin role only — both controllers `before_action :require_admin`, and the sidebar link is hidden from writers, since webhooks can exfiltrate subscriber emails): `Admin::WebhooksController` (full CRUD at `/admin/webhooks`) shows the signing secret once via flash on creation or regeneration (`POST .../regenerate_secret`), and a "Send Test Event" button (`POST .../test`) enqueues a `ping` event bypassing subscription filtering. `Admin::WebhookDeliveriesController` (`/admin/webhooks/:webhook_id/webhook_deliveries`) shows the delivery log (event, response code, timestamp, success/fail) for one webhook.

## Outbound HTTP (SSRF Guard)
`Outbound::Connection.request(uri, net_http_request, max_bytes:, truncate: false)` (`app/services/outbound/connection.rb`) is the one guarded connection for attacker-controlled URLs, shared by `Webhooks::Sender` and `ActivityPub::HttpClient`; those classes only build the request and map statuses/errors. It calls `Outbound::UrlGuard.resolve!` (every DNS answer must be public, else `UrlGuard::UnsafeUrlError` before anything is sent) and pins the socket to that vetted IP with `Net::HTTP#ipaddr=`, so a DNS rebind between check and connect can't reach an internal address. It never follows redirects (a 3xx comes back as a status), sets 5s open / 10s read / 10s write timeouts, and streams the body: past `max_bytes` it raises `Outbound::Connection::ResponseTooLarge`, or with `truncate: true` stops reading, closes the connection and returns the first `max_bytes`. It returns `Response(code, body, truncated)` and lets network errors propagate. `Outbound::UrlGuard` (`blocked_host?`, `blocked_ip?`, `resolve!`) is also what `Webhook` URL validation uses; its error messages are deliberately feature-neutral. Don't open a `Net::HTTP` to a user- or remote-supplied URL anywhere else. `test/services/outbound/connection_test.rb` proves pinning, no-redirect and the cap against a real loopback socket (the host is `pinned.invalid`, which can't resolve, so reaching the server proves the pin). `OembedFetcher` deliberately doesn't use it: its endpoints are fixed provider hosts, not user input.
